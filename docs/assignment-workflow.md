# OOP2 作業工作流

目標：依題目自動實作、整理證據並提交 GitHub PR，再提供讓學生理解原理與設計方式的說明，由使用者確認後合併。

本文件是可跨對話重新讀取的流程依據。它不代表任何一份作業已完成，也不會增加工具、GUI 或 GitHub 的存取權限。

## 1. 界定本次範圍

先檢查 repo 最新狀態、目標作業與既有 PR，再向使用者說明：

- 目標：週次、作業編號、題目及本次要完成的部分。
- 變更：預計新增或修改的檔案／目錄；若需更新週次與根目錄索引，也列入。
- 驗收：從題目整理可檢查的功能與繳交條件。
- 不包含：本次不處理的其他作業、功能或共用改動。

需求明確即可開始；缺少會影響實作的規格時先釐清。範圍擴大需先取得確認，並更新 PR 描述。只要求整理結構或修正部分內容時，不自行擴大成完成整份作業。

## 2. 實作與理解

依題目及老師限制實作，沿用現有專案慣例。除非題目或使用者需要，不增加額外套件、建置工具或無關功能。

完整作業以以下位置保存資料；部分任務只修改本次範圍涉及的檔案：

| 位置（相對於 weekNN/assignmentNN/） | 內容 |
| --- | --- |
| README.md | 題目摘要、規格、檔案連結、環境需求、執行方式與繳交清單 |
| src/ | 程式碼；加入程式後移除不再需要的 .gitkeep |
| TESTING.md | 實際測試環境、操作步驟、預期／實際結果、證據及未驗證項目 |
| screenshots/question-01.png | 選填：僅使用者特別要求時列為必要資料 |
| screenshots/result-01.png | 實際執行結果截圖 |
| AI-CONVERSATION.md | AI 協作對話紀錄，標示為整理紀錄或逐字稿；可取代對話截圖 |
| screenshots/README.md | 截圖說明與索引，只連結已存在的檔案 |
| Reflection.md | 使用者的學習反思，標示是否經本人確認 |
| EXPLANATION.md | 程式原理與設計說明 |

截圖保留原始格式的正確副檔名；表中的 PNG 是命名範例。沒有取得的檔案不得以假圖補齊。

EXPLANATION.md 包含：程式目的與操作流程、類別／元件分工、事件及資料流、關鍵語法、設計原因、如何執行與驗證。以有基礎程式能力的學生為起點，必要時用小段程式碼解釋，避免逐行重述整份程式。

## 3. 實際驗證與擷取證據

1. 執行適合作業的編譯與功能檢查。
2. 有可操作的 GUI 環境時，實際啟動程式、操作並截圖；無法操作時如實記錄限制；僅針對使用者要求的必要結果請求補充，不追加額外驗證門檻。
3. 在 TESTING.md 記錄測試日期、環境／版本、步驟或命令、預期結果、實際結果及通過／失敗／未執行狀態。
4. 修正範圍內的問題並重測受影響項目。不要把編譯成功寫成所有功能通過。
5. 題目原圖預設選填，不列為缺件、不反覆索取。以已提供的題目整理 README 規格；核心規格有疑問才提問。使用者特別要求原圖時才收集。
6. AI 對話可用 AI-CONVERSATION.md 整理，清楚標示非逐字稿時為重點整理；繳交項目名稱用「AI 對話紀錄」。無須額外要求對話截圖。

截圖只包含作業相關畫面，避免帶入密鑰或無關個人資料。工具受限時先完成不受影響的工作，明列仍缺少的證據。

### 骰子模擬器驗收範例

- 視窗標題、400 × 320 尺寸、開啟置中及關閉結束程式符合題目。
- 中央點數字體為 60pt，下方有擲骰按鈕。
- 點擊後點數介於 1～6，次數逐次加一，總和與平均值正確。
- 點數 1 為紅色、6 為綠色，其餘為黑色；平均值保留兩位小數。
- 保存一般點數、1 與 6 的實際畫面；若未觀察到某情境，如實標示未驗證。
- 原程式初始點數 0 代表尚未擲骰，README 應說明此行為。

此清單說明骰子題目的功能要求，不代表每一條都要追加獨立動態證據。未特別要求時，不把關閉程序、完整逐次累計、顏色轉換連續證據或尺寸／字體／置中實測列為待補或交付門檻。已做檢查如實記錄，未直接驗證的限制可留在測試紀錄，不當成失敗。仍須完成題目功能、適當編譯與基本檢查，處理已發現的錯誤。其他作業也遵循相同原則。

## 4. 整理 Reflection 與完成狀態

驗證後請使用者提供實際學到的概念、遇到的問題與解法，以及想改進之處；已有回饋就直接整理，不重複詢問。

可提交待確認的整理稿，但不得把推測寫成使用者真實經驗。沒有回饋時保留提示並標記待填寫。先前對話中的心得只有經本人確認後，才能標記完成。

檢查程式、測試紀錄、執行截圖、AI 對話紀錄及 Reflection 是否齊全；題目原圖僅在使用者特別要求時納入，再同步更新作業、週次與根目錄 README 的狀態。原理說明也應交付；模板存在不代表內容完成。

## 5. 自動提交與 PR 審查

從適當的最新基底建立獨立分支，每份作業一個 PR。已有同目的的開啟中 PR 時，先確認分支與內容，再更新該 PR；不覆蓋使用者的新變更。

提交前檢查：

- 變更檔案與開頭界定的範圍一致，沒有其他作業或無關改動。
- 相對連結、圖片路徑及執行指令符合實際目錄。
- 沒有編譯產物、密鑰或無關檔案。
- 測試與完成狀態有實際證據，未完成事項清楚可見。

PR 描述固定包含以下資訊：

### 變更範圍

具體問題、完成後行為、變更檔案／目錄及原因。共用索引的更新也列出。

### 驗證結果

列出實際執行的檢查及結果；未驗證項目另列，不以「測試通過」籠統帶過。

### 待補／待確認事項

逐項列出缺件、未通過的必要測試與尚未確認的個人心得；無則寫「無」。完整作業仍有必要缺件時，使用 Draft PR。未要求的題目原圖與額外直接驗證不是必要缺件，不得因此維持 Draft 或追問。單純文件或結構 PR 不因範圍外的作業缺件而被當作未完成，但必須說明它不是完整作業交付。

### 使用者審查重點

提供具體可檢查的重點：是否符合題意、必要操作結果、心得是否符合本人經驗，以及是否有範圍外變更。連結到相關檔案或證據，避免只要求「請檢查 PR」。

## 6. 最終交付與合併

回覆 PR 連結、完成內容、驗證結果與限制、原理說明文件連結，以及需要使用者確認的事項。

自動提交到分支及建立 PR 不等於自動合併。只有使用者明確確認合併後才合併至 main；不把沉默或提出其他問題視為合併授權。GitHub 寫入受阻時保存成果並說明未完成的步驟。
